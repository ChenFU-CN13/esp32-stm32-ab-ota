# W25Q128 单备份区回滚 + IWDG 看门狗 + APP 升级闭环 方案设计

> 状态：设计稿（未动代码）
> 目标：让 Bootloader 具备「升级失败/启动校验失败/卡死复位时自动回滚到上一可用版本」能力，
>       并打通「生产 APP」端真正的升级闭环（0x01 监听 + 重启进 bootloader + 版本显示）。
> 依据约定：一切改动人 `ota_storage`（回滚地基）、`ota_core`（回滚决策）、APP 端（升级通知监听），沿用「只挪不改 + 分层归口」约定。

---

## 〇、当前真实链路（测试阶段）与目标链路

### 当前实测链路
```
testB(bootloader) → 跳转 → testA(A区测试程序) → 空闲等 ESP32
                                              → 收到 0x01 升级通知 → 重启回 testB
                                              → 升级完成 → 跳转到真正的 APP(智能温湿度系统)
```

### 关键差距
称"testB" 实为 Bootloader；真正的**生产 APP 目前没有实现「监听 0x01 → 重启进 bootloader」**。
现在整套能跑通，是靠 A 区临时放了 `testA` 承担"收通知+重启"。**生产 APP 的升级闭环还没接通**。

### 推进顺序（方案甲：先打通生产闭环，再做回滚）
1. **阶段 1**：给生产 APP 补上 0x01 监听 + 重启进 bootloader + LVGL 版本显示，让"生产形态"首尾跑通。
2. **阶段 2**：实现 W25Q128 单备份区回滚（本方案文档主体），可用 testA 场景先测回滚。
3. **阶段 3**（可选加固）：IWDG 看门狗检测卡死/掉电复位，联动回滚。

## 一、现状与痛点

当前防变砖策略是**被动防护**：
- 整体 CRC 失败 → 置 `s_app_firmware_invalid` → Bootloader 停在 IDLE 等待，不跳转损坏 A 区。
- 缺点：旧版本固件被擦除后**没有退路**，只能等 ESP32 重传新固件或 SWD 手动恢复。升级中断电/跑飞也无法自动自愈。

**本方案目标**：升级前先把旧 A 区固件整份备份到 W25Q128，升级失败/启动校验失败时自动回滚。

---

## 二、存储资源分配（按你的取舍收敛为「单备份区 + AT24C02 存元数据」）

### 2.1 W25Q128（外部 SPI Flash，16 MB）——只留一个纯备份区

按「单备份区」收敛：A 区永远是运行目标，W25Q128 仅作为"旧固件保险箱"，**不再做双镜像 A/B 切换**。

| 区段 | 起始地址 | 大小 | 用途 |
|---|---|---|---|
| **备份区**（旧固件） | `0x000000` | 960KB | 升级前把 A 区当前固件整份拷入 |
| 空闲/预留 | `0x0F0000 ~ 0x1000000` | ~15MB | 健康测试、断点续传预留 |

> 为什么 960KB：APP 固件实测约 475KB，A 区上限 960KB，按上限预留最稳。
> 为什么砍掉元数据扇区：这些标志几十字节，放 AT24C02 足够（见 2.2），无需在 Flash 上先擦再写。

### 2.2 AT24C02（EEPROM，2 Kbit = 256B）——元数据全在这

| 地址 | 大小 | 内容 |
|---|---|---|
| `0x00 ~ 0x4B` | 76B | 现有 `OTA_INFOCB`（运行信息：版本/大小）——保持兼容不动 |
| `0x4C` | 72B | **回滚旧版本记录**（旧版本号+旧大小） |
| `0xA4` | 16B | **更新日期时间戳**（每次升级成功写入） |
| `0xB4` | 8B | 关键标志：`backup_valid`(0xA5 备份有效) / `upgrade_state`(IDLE/UPGRADING/COMMIT/NEED_ROLLBACK) / 跳转原因 |
| `0xBC ~ 0xFF` | 预留 | 断点续传 offset 等 |

> 关键决策字段用**单字节**（如 backup_valid=0xA5），EEPROM 字节级随机写、写前不擦，
> 单标志一把写就带过去了，天然抗掉电撕裂，比 Flash 元数据扇区+双副本简单得多。

## 三、回滚触发时机（双重触发）

### 3.1 触发点 1：启动跳转前校验
Bootloader 拉起后跳 A 区前，先读当前 A 区镜像 CRC：
- 校验通过 → 直接跳转。
- 校验失败 → 若 `backup_valid` 且备份完好 → 从 W25Q128 回滚后跳转。

### 3.2 触发点 2：升级失败时
不可恢复 NACK（`0x04` 落盘错误 / `0x05` 整体 CRC 失败）、ABORT 已擦坏 A 区、IWDG 复位重启等 → 走回滚流程。

### 3.3 回滚执行流程（在 `ota_core` 触发，`ota_storage` 落地）
```
检测到 A 区损坏 / 升级失败
  → 读 AT24C02 backup_valid 确认有可用备份
  → 从 W25Q128 备份区整份读回 + 校验 CRC（惰性校验：备份完好才继续）
  → 擦除 A 区 Flash
  → 从备份区写回 A 区
  → 回读 A 区整份 CRC 比对（防写坏，冗余务必保留）
  → 恢复 AT24C02 旧版本号/大小/日期
  → 打印回滚成功，跳转旧版本 A 区
```

## 四、IWDG 看门狗加固（可选，阶段 3）

| 项 | 设计 |
|---|---|
| 初始化 | Bootloader 用独立看门狗，约 **3~5s** 超时 |
| 喂狗点 | 只在外围**耗时段**喂：Flash 擦除、W25Q128 搬移、回滚写回各分块喂一次 |
| 关键坑 | 升级全程是长时间阻塞操作，若不在耗时操作内喂狗会**误复位**——最易踩的点 |
| 派生检测 | IWDG 复位后读复位标志，若处于 `UPGRADING` → 判定升级中断 → 触发回滚 |
| 调试 | 使能 `__HAL_DBGMCU_UNFREEZE_IWDG()`，否则调试断点期间狗被冻结不计数 |

## 五、CRC 校验分工（回应"会不会浪费时间"）

CRC 校验本质是**读**（SPI 读 475KB 仅几十 ms），真正贵的是**擦除/写入 Flash**（秒级）。多趟校验开销可忽略。各管一段落盘正确性，不重复：

| 校验 | 对象 | 时机 | 归属 |
|---|---|---|---|
| 传输层帧 CRC | 每帧 | 收帧时 | 已有，不新增 |
| 落盘层整体 CRC | **新固件**写进 A 区 | 升级结束 | 已有，不新增 |
| 备份校验 | 旧固件拷进 W25Q128 | 备份时 | **新增，立即校验，写坏可重备** |
| 写回校验 | 回滚后 A 区内容 | 回滚时 | **新增，冗余务必保留，防真机变砖** |

## 六、模块改动落点（沿用分层约定）

| 模块 | 改动 | 归口 |
|---|---|---|
| `ota_storage.c/h` | 新增 W25Q128 备份/回滚落盘函数：读 A→写备份区、读备份→擦 A→写回、分块 CRC | 回滚地基 |
| `ota_core.c/h` | 新增回滚决策：整体 CRC 失败 / ABORT 已坏 / IWDG 复位检测 → 调 `ota_storage` 回滚 | 回滚决策 |
| `bootloader.c/h` | 启动跳转前增加「先校验当前 A 区 CRC，坏则回滚」分支 | 跳转决策 |
| `AT24C02` | 写入回滚记录/更新日期/跳转原因/backup_valid/upgrade_state | 元数据落盘 |
| **生产 APP** | 阶段 1：0x01 监听 → 置跳转原因(0xBA) → 重启进 bootloader；LVGL 显示版本 + 自主选择重启时机 | APP 升级闭环 |
| `crc32` | 复用 W25Q128 既有 CRCC32 表，不重复造轮子 | — |

## 七、测试用例计划（烧录回归）

1. **用例 R1（正常升级）**：备份旧固件 → 新固件写 A 区 → 整体 CRC 通过 → 提交，跳转新版 APP。验证备份/提交正确。
2. **用例 R2（整体 CRC 失败回滚）**：新固件写盘时注入错误 → 触发回滚 → 跳转回旧固件。
3. **用例 R3（升级中途断电/IWDG 复位）**：升级中途断电重启 → 读 upgrade_state=UPGRADING → 自动回滚旧版本。
4. **用例 R4（看门狗防卡死）**：耗时操作处停喂 → 超时复位 → 检测并回滚。
5. **用例 A1（APP 升级闭环）**：生产 APP 运行中收到 0x01 → 置跳转原因重启回 bootloader → 完成升级 → APP 显示新版本。

## 八、待确认的开放问题

1. **喂狗超时与升级耗时匹配**：Flash 960KB 擦除+写入约 1~3s，需实测确定 IWDG 预分频，建议 ≥ 单个耗时子块（每 256KB）处理时间。需要实机确认或我给估算值？
2. **回滚后是否自动重试升级**：回滚到旧固件后，是否要求 ESP32 重新触发一次升级？（默认：不自动，等待再次收到通知）
3. **AT24C02 起始地址边界核对**：现有 `OTA_INFOCB` 写入用的是 `EP24C_WriteLongData(0, ...)`（76B），从 `0x4C` 起放新字段需确认驱动是否支持任意地址写、以及 AT24C02 实际页大小（通常 8 字节页）避免跨页撕裂——**这块需要读 AT24C02 驱动确认**。
