# 2.0.5 累计式环形缓冲区更新与后续测试准备

更新日期：2026-10-29。本次更新标为 `2.0.5`，同步 APP、Bootloader 和 ESP32 日志调整，保留用户手写代码，不新增 Python 测试程序。APP 的版本文字修改仅为启动调试打印，不涉及版本管理逻辑。

## 本次代码变化

| 范围 | 更新内容 |
|---|---|
| STM32 APP | USART2 接收环改为 `uint32_t wr/rd` 累计计数，通过差值判满、掩码访问数组；64 字节数组可全部使用，保留满时拒收新字节和溢出计数接口。数据写入或读出完成后才发布对应计数。 |
| STM32 Bootloader | 8192 字节软件环改为累计计数；DMA 接收片段只有在剩余空间足够时才整批转存，否则整批拒收并累计拒收字节，避免覆盖未读数据。新增容量检查与拒收计数查询接口。 |
| Bootloader 初始化与回显 | 初始化分别清零读写计数，清除空闲标志，检查 DMA 启动结果后开启空闲中断；独立回显测试改用带超时的阻塞发送，避免函数返回后 DMA 继续访问局部数组。 |
| APP 其他调整 | 启动调试文字改为 `2.0.5`；`uart2_comm.c` 移除直接包含的 `main.h`，当前仍由 `APP_Tasks.h` 等头文件间接引入。启动文字本身不负责修改 OTA 元数据或 EEPROM 版本。 |
| ESP32 | 注释 OTA 独占分支的 `[UART][DROP] OTA busy` 警告输出；事件消费和 OTA 任务读取 ACK/NACK 的逻辑保持不变。 |
| 调试材料 | 收录用户保存的 STM32 正常升级原始日志，便于后续对比。 |

## 验证证据与边界

- 仓库保存的[正常传输日志](../debugging/ota-transfer/STM32端升级调试日志记录(正常传输情况下).txt)记录了 2026-10-28 的 `2.0.3` 升级：424 包、433372 字节，CRC32 为 `0xF1EA1FA8`，校验后启动 APP 并完成版本确认。这是历史记录，不能当作当前全部修改的回归证据。
- 用户随后在会话中提供的 `2.0.4` 实机日志显示：424 包、433384 字节，实际与期望 CRC32 均为 `0xB3A74AA2`，跳转 APP 后完成版本确认并恢复心跳。该段原始日志未另行保存到仓库文件。
- 用户提供的 ESP32 片段中，`event type=0` 对应当前 ESP-IDF 5.3.4 的 `UART_DATA`；普通接收任务只跳过事件，OTA 任务读取应答，升级进度持续推进。该片段没有显示 NACK 或超时重试，但不能证明整个升级过程没有重试。
- 当前 APP 启动提示为 `2.0.5`，尚无本轮对应的完整升级日志。本次 Git 同步没有重新执行 Keil/ESP-IDF 编译、烧录或实机测试。
- 先前的电脑端算法检查覆盖过 Bootloader 软件环的满空、整批拒收、数据顺序和累计计数回绕；它不等于 MCU 中断、DMA 时序或硬件并发测试。

## 保留的边界

- Bootloader 的拒收计数只记录软件环拒收字节；当前协议流程没有读取该计数来立即触发 NACK，恢复仍依赖原有超时和重试机制。
- DMA 停止和重新启动的接收窗口、DMA 满缓冲处理、任意拆包与连续帧解析仍需专项验证；累计式软件环并不自动解决这些问题。
- 当前 ESP32 注释掉的日志覆盖 `UART_DATA`、`UART_BUFFER_FULL` 和 `UART_FIFO_OVF` 三类事件。正常数据事件不需要逐包告警，但后两类异常也因此失去该处的提示；后续应分别处理日志等级，不能把溢出事件一并认作正常忙状态。

## Python 测试接入顺序（待实施）

1. 先做命令行测试程序，通过 USB 转串口替代 ESP32，与 STM32 升级串口通信；调试串口独立记录日志，测试期间只保留一个协议发送方。
2. 先使用可运行的 APP 固件完成正常升级，再加入错误数据 CRC、重复包、错误序号和阶段超时用例。每个用例明确前置状态、预期应答、恢复步骤和最终判断。
3. 再让 Python 模拟 STM32，测试 ESP32 的 ACK 缺失、NACK、异常响应和重试上限。
4. 最后扩展到 OneNET 完整链路与批量回归；记录固件标识、串口参数、原始收发数据、耗时和结果。以上项目目前均为计划，不代表已有自动测试覆盖。

后续技术栈讨论围绕项目实际问题展开：协议字节流解析、接收异常恢复、FreeRTOS 任务通信与资源观测、电脑端 C 算法测试，以及成熟后加入持续集成。每项先明确要解决的问题和验收条件，再决定是否引入。
