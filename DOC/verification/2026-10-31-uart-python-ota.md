# 串口组帧与 Python OTA 测试验证

更新日期：2026-10-31。实机操作、编译及烧录由项目作者执行；本页区分保存的采集记录、截图确认和离线模拟，不将三者混写。

## 本次解决的问题

串口接收到的是连续字节。一次接收可能只有半帧，也可能包含多个帧。此前已有累计式软件环，但 Bootloader 将“当前收到的全部字节”直接交给协议处理，仍会将半帧误判为报文错误。

实测将一帧 1037 字节数据拆成 `8+1029` 字节、间隔 50 ms，旧处理先回长度错误 `NACK 0x03`，再回包头错误 `NACK 0x01`。Python 发送 ABORT 后又读到残留 NACK，提前结束采集，缺少实际恢复的完整记录。

本次在原有 8192 字节软件环上补齐按协议长度提帧，并把 Python 的失败用例判定与异常收尾分开。优化目标是串口接收和错误恢复的可靠性，波特率仍为 115200，保持逐包 ACK 与升级前备份。

```mermaid
flowchart LR
    UART[USART2 DMA / IDLE] --> Ring[累计式软件环]
    Ring --> Reader[OTA_ReadFrame]
    Reader -->|字节不足：留在环里| Ring
    Reader -->|只取一帧，保留后续字节| Protocol[命令 / 状态 / CRC 检查]
    Protocol --> Storage[写 Flash / 提交 / 回滚]
```

## 实现要点

| 改动 | 具体行为 |
|---|---|
| 软件环增加 `PeekData`、`Clear` | 查看头部不推进读计数；超时或字节不连续时清理当前残留。 |
| 统一 `OTA_ReadFrame()` | 简单命令等齐 3 字节，信息帧等齐 25 字节，数据帧先等齐 8 字节头，检查载荷 1～1024，再等待完整 `8+payload+5` 字节。 |
| 每次只消费一帧 | 半帧保留，多帧逐帧提取；CRC、帧尾和状态仍由协议处理检查。 |
| 命令与长度共同分流 | 避免 12 字节载荷形成的 25 字节数据帧被误判为信息帧。 |
| 阶段超时先行 | 无效帧持续进入时仍可触发超时；噪声扫描按当前可用字节有界执行。 |
| ISR 保持搬运职责 | DMA 回调不做协议解析、Flash 写入或回滚。 |
| Python 有界收尾 | 一次 ABORT，限时等 ACK 和旧 APP；允许阶段内有限识别残留应答，保留原始失败。 |
| 恢复证据分开记录 | `protocol_pass`、`cleanup.success`、`recovery_crc.match` 分别表达用例、收尾、镜像恢复结论。 |

代码入口：[command.c](../../STM32-OTA/testB3/Drivers/bootloader_drivers/src/command.c)、[ota_core.c](../../STM32-OTA/testB3/Drivers/bootloader_drivers/src/ota_core.c)、[Python 测试目录](../../Python_test/README.md)。

## 代表性实机结果

Python 测试固件为 2.0.7，433320 字节、CRC32 `D4977540`，共 424 包。下表为修改后实测，具体运行编号及字段见 [公开结果摘要](2026-10-31/results.json)，镜像恢复和校验见 [日志摘录](2026-10-31/stm32-excerpts.txt)。

| 用例 | 注入或操作 | 实测结果 |
|---|---|---|
| 两段拆帧 | `seq=10`，8+1029 字节，间隔 50 ms | 完整帧收齐后 ACK，继续升级，整体 CRC 和 APP 版本通过。 |
| 七段拆帧 | 1、1、6、512、512、4、1 字节，间隔 50 ms | 覆盖头部、数据、CRC、尾部附近分界；最终 CRC 和 APP 确认通过。 |
| 相邻两帧粘连 | seq 422/423，1037+181=1218 字节一次提交 | 收到两次 ACK，实际 168 字节末包正确接收，整体 CRC 通过。 |
| 整体 CRC 拒收后再次升级 | 真实 CRC `D4977540`，声明 `D4977541` | 得到 `NACK 0x05`；ABORT 和恢复完成，随后正常升级通过。 |
| 主动 ABORT 后再次升级 | 确认 10 包后立即 ABORT | ACK、旧版本、恢复 CRC 通过；保持运行后重新发起完整升级成功。 |
| 数据超时后再次升级 | 确认 10 包后静默 16 秒 | 恢复通知 `NACK 0x08`、ABORT 收尾、旧版本与 CRC 通过；紧接着正常升级成功。 |
| 实际断电 | 确认 212/424 包后拔整板 USB | 重新上电检测到未完成升级，恢复 CRC 与备份一致，旧 APP 2.0.7 启动。 |
| ESP32-S3 正常 OTA | OneNET 下发 2.0.8，未主动注入故障 | STM32 整体 CRC 通过，APP 版本确认 2.0.8，平台确认 step 201，Manager 回 IDLE，MQTT 业务通信继续。 |

三组“异常恢复→再次升级”的来源分别是：

- `fwcrc_capture_20261031_004917_351389` → `upgrade_capture_20261031_005510_862863`。
- `abort_capture_20261031_080032_639631` → `upgrade_capture_20261031_080443_746180`。
- `timeout_capture_20261031_080940_037636` → `upgrade_capture_20261031_081032_542086`。

这些编号便于对照摘要，原始逐字节采集不随仓库上传。恢复后再次升级按连续测试流程执行，不通过手动复位或重新烧录清理会话。

## 实际断电的记录方式

确认 212 包后停止发送，约 2.078 秒检测到板载调试串口消失，操作者确认整板断电。重新插 USB 前按住 RESET，待脚本重开端口后再松开，保留启动恢复日志：

```text
[回滚] 检测到未完成升级，进入启动恢复
[回滚] 恢复成功，CRC32=0xD4977540
```

备份 CRC 同为 `D4977540`，旧版本确认为 2.0.7。USB 消失是枚举证据，电源断开由操作者确认；本次断电发生在半份固件已写入、尚未提交的阶段，不声称精确发生于某次 Flash 编程脉冲内。按住 RESET 用于提前接好采集，实际拔 USB 已先完成。

## 性能及覆盖边界

修改后代表性 Python 正常升级：有效固件 433320 字节，备份擦除 13.244 秒、数据阶段 54.847 秒、整体校验及应答 0.327 秒；通知至 APP 版本确认 71.115 秒，有效数据速率约 7.72 KiB/s。计时包含主机等待与版本查询，不包含 OneNET 下载，也不等于精确跳转时刻。

- 接收 8+1029 和七段拆分已实测，简单命令/信息帧的拆分、其他间隔尚未全部覆盖。
- 粘连测试是相邻不同数据帧，并非当前包与重复包粘连；一次 write 不等于一次 DMA 回调。
- 单包 CRC、重复包、错序包另有早期实机记录，本轮未在修改后的 Bootloader 上全部重跑。
- 断电和最终 ESP32 正常 OTA 各做一次关键用例，不推导多轮成功率、所有断电窗口或干扰恢复结论。
- ESP32 ABORT 后整次重试仍有旧状态假设，跨轮任务缓存复用也未完成；正常 OTA 成功不替代异常自动重试验证。
- 本次发布前执行的 23 个 Python 测试方法使用模拟串口；没有在发布操作中再次编译、烧录或连接真实串口。
